## Context

当前系统在 `backend/anticheat/anticheat.go` 中有基础的反作弊组件：
- `FastReactionChecker`：仅记录快速反应次数
- `SuspiciousActivityDetector`：基于时间窗口的频率检测
- `CheatReportManager`：简单的举报管理

现有的判定逻辑：快速反应计数 > 0 或频率超过阈值则标记为作弊。这种二值判定容易产生以下问题：
1. **误判高**：合法玩家的正常快速反应被误判
2. **难以区分**：无法区分轻微异常和明显作弊
3. **无申诉机制**：被误判的玩家无处申诉
4. **缺乏透明度**：玩家不知道为什么被标记作弊
5. **运营成本高**：管理员无法高效筛选真实的作弊案例

数据库模型已存储 `CheatDetected` 和 `CheatUIDs`，需扩展以支持风险分数、处罚记录、申诉信息。

## Goals / Non-Goals

**Goals:**
- 实现多维度的风险评分模型，综合考虑响应时间分布、操作频率、胜率异常、账号特征等
- 替换二值判定，改为 0-100 的风险分数，支持阈值配置
- 支持渐进式处罚：观察(20-40) → 警告(40-60) → 禁言(60-80) → 封号(80-100)
- 实现完整的举报、申诉、人工审核工作流
- 提供管理员仪表板查看、搜索、人工审核检测结果
- 记录完整的审计日志便于事后分析和模型优化
- 给予玩家知情权和申诉权

**Non-Goals:**
- 不涉及账号封禁的具体执行逻辑（封禁实现由其他模块负责）
- 不实现自动撤销处罚（由管理员手动处理）
- 不设计复杂的机器学习模型（仅使用规则和统计方法）
- 不涉及用户认证系统的改变

## Decisions

### 1. 风险评分架构 vs 多个独立检测器
**决策**：采用统一的风险评分框架，将多个检测器的结果组合成单一分数。

**理由**：
- 便于理解和解释（一个数字比多个布尔值清晰）
- 支持权重调整，易于优化
- 便于设定处罚阈值

**替代方案**：
- 多个独立检测器分别决策（复杂度高，难以协调）
- 规则引擎（过于复杂，不必要）

### 2. 检测维度的选择
**决策**：实现 5 个核心检测维度：
1. 响应时间异常（Response Time Anomaly）：统计分布分析
2. 操作频率异常（Operation Frequency Anomaly）：时间窗口检测
3. 胜率异常（Win Rate Anomaly）：与历史平均值对比
4. 操作模式异常（Pattern Anomaly）：相邻操作时间间隔异常
5. 账号新旧程度（Account Age Risk）：新账号可疑度更高

**理由**：
- 涵盖了自动化作弊的主要特征
- 数据易于收集和计算
- 避免过度复杂

### 3. 权重配置方案
**决策**：使用配置文件定义各维度的权重和阈值，支持动态加载。

```yaml
anticheat:
  dimensions:
    response_time:
      weight: 0.25
      threshold: 100ms  # 正常范围
      percentile: 0.05  # 识别异常的百分比
    frequency:
      weight: 0.25
      threshold: 20  # 每10秒最多20个操作
    win_rate:
      weight: 0.20
      threshold: 0.85  # 胜率超过85%视为异常
    pattern:
      weight: 0.15
      threshold: 50ms  # 相邻操作间隔 < 50ms
    account_age:
      weight: 0.15
      young_account_days: 7  # 7天内的账号权重加倍
  
  sanctions:
    observe: 20   # 20-40 观察
    warning: 40   # 40-60 警告
    mute: 60      # 60-80 禁言
    ban: 80       # 80-100 封号
```

**理由**：
- 配置文件便于运维调整
- 支持 A/B 测试不同权重

**替代方案**：
- 硬编码阈值（难以优化）
- 数据库配置（过度复杂）

### 4. 申诉流程
**决策**：三层审核制度：
1. 自动检测 → 风险分数
2. 玩家申诉 → 状态变为"待审核"
3. 管理员审核 → 确认或推翻

**理由**：
- 保护玩家权益
- 帮助改进模型（审核结果可用于重新训练）

### 5. 数据模型扩展
**决策**：新增数据库表：
- `cheat_risk_scores`：存储每场游戏的风险评分和维度分数
- `cheat_sanctions`：存储处罚记录（警告、禁言、封号等）
- `cheat_appeals`：存储玩家申诉
- `cheat_audit_logs`：审计日志（所有检测和处罚决策）

**理由**：
- 解耦不同关注点
- 便于查询和分析
- 支持完整的生命周期追踪

## Risks / Trade-offs

| 风险 | 影响 | 缓解策略 |
|------|------|---------|
| **误判风险** | 合法玩家被误判为作弊 | 设置较高的自动处罚阈值，提供申诉机制，人工审核 |
| **漏检风险** | 真实的作弊者逃脱检测 | 定期分析漏检案例，优化权重；依靠玩家举报补充 |
| **性能风险** | 风险计算增加 CPU 负担 | 异步计算，缓存历史统计数据，定期批处理 |
| **玩家体验** | 被标记异常可能影响满意度 | 在应用处罚前告知原因，提供申诉渠道，审查周期透明 |
| **管理员负担** | 需要人工审核申诉和特殊案例 | 提供清晰的管理界面，自动生成分析报告 |

## 架构图

```
游戏进行中
    ↓
[多维度检测器] (响应时间、频率、胜率、模式、账号年龄)
    ↓
[风险评分引擎] → 综合多个维度 → 生成 0-100 的风险分数
    ↓
[处罚决策层]
    ├─ 观察(20-40)：标记但不处罚，记录日志
    ├─ 警告(40-60)：向玩家发送警告信息
    ├─ 禁言(60-80)：限制聊天功能
    └─ 封号(80-100)：触发账号封禁流程
    ↓
[数据持久化] → 风险分数表、处罚记录表、审计日志
    ↓
[申诉和人工审核] → 玩家可申诉、管理员可推翻决策
```

## 开放问题

1. **性能基准**：需要确定风险计算的 P99 延迟要求（< 100ms？）
2. **历史数据**：如何处理历史数据中的 `CheatDetected` 字段的迁移？
3. **申诉 SLA**：管理员应在多长时间内处理申诉（1 天？3 天？）
4. **跨游戏追踪**：是否需要跨游戏类型共享玩家风险分数？
5. **隐私**：风险分数对玩家是否完全透明，还是仅显示处罚类型？
