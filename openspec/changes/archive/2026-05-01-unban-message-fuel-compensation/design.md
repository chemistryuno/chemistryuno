# 设计说明（How）

目标：在管理员确认解封用户的流程中，添加统一的解封消息发送与燃素补偿发放。设计需满足可配置、幂等、具备审计记录和回滚能力。

关键点：
- 配置项：在 `config/anticheat.yaml`（或已有配置文件）新增：
  - `unban.compensation_amount`：默认 `100`（燃素）
  - `unban.default_message`：默认文案（见 proposal）

- 后端实现位置（建议）：
  - 业务逻辑：`backend/anticheat/appeal.go`（或现有处理解封的后端包）
  - HTTP 处理：`handlers/appeal.go`（管理员触发点）
  - 仓库/持久化：`repository/user_repository.go`（添加 `AddFuel(userID, amount) error` 方法）

- 工作流与事务：
  1. 管理员在控制台触发解封请求。
  2. 服务端在事务中执行：
     - 将用户状态更新为“已解封”。
     - 向用户发送系统消息（使用现有通知/消息队列模块）。
     - 调用仓库函数发放燃素（`AddFuel`）。
     - 在审计表/日志中记录补偿详情（含金额、模板、管理员 ID、时间戳）。
  3. 若中间任一步骤失败：
     - 根据失败阶段决定回滚策略（强烈建议：对发放失败时，标记补偿失败并发送告警，而不要在没有补偿的情况将用户置为已解封；或至少记录为“需人工补偿”）。

- 幂等性：
  - 在用户补偿记录中写入唯一补偿记录（例如：`unban_compensation:{user_id}:{unban_event_id}`），发放前做存在检测，避免重复发放。

- 消息模板：
  - 将默认文案放在配置中，允许运营在不改代码的情况下调整文案和金额。
  - 支持占位符：`{admin_name}`, `{compensation_amount}` 等。

- 审计与监控：
  - 在原有的解封审计记录中增加字段 `compensation_amount`、`compensation_status`、`compensation_note`。
  - 提供简单监控告警：当短时间内补偿失败率异常升高时告警给运营/开发。

- 安全与权限：
  - 仅管理员或具备相应权限的接口可触发自动补偿流程。

兼容性与迁移：
- 优先通过在代码中扩展现有审计记录（无需新 DB 表）。如果现有审计模型无法扩展，再提交单独迁移提案。

测试：
- 单元测试：仓库层 `AddFuel` 成功/失败的模拟，消息模板渲染测试。
- 集成测试：模拟管理员解封流程，覆盖正常成功路径与补偿失败的降级路径。
